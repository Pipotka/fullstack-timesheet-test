## Принятые допущения

На момент выполнения задания ответы на часть уточняющих вопросов не были получены. Поэтому по спорным местам спецификации я зафиксировал следующие допущения.

### 1. Маршруты и методы из ТЗ

Я реализовал контракт по путям из ТЗ, но использовал семантичные HTTP-методы:

- `POST /api/time-entries` — создание записи;
- `PUT /api/time-entries/{id}` — изменение записи.

В таблице задания указаны `PUT /api/time-entries` для создания и `POST /api/time-entries/{id}` для изменения. Поскольку ответ на этот вопрос не был получен, я зафиксировал допущение, что важны сами маршруты и требуемое поведение, а методы можно привести к более стандартной REST-семантике. При необходимости вернуть строгое соответствие таблице можно заменить только методы без изменения бизнес-логики.

### 2. Изменение ставки сотрудника для сценария 8

В таблице нет пользовательского интерфейса или справочника для редактирования сотрудников и ставок, но сценарий 8 требует изменить ставку задним числом.

Я принял допущение, что изменение ставки можно выполнить отдельным служебным механизмом, а не через пользовательский интерфейс. В моей реализации изменение ставки выполняется отдельным скриптом или служебным запросом, а описание этого действия добавлено в `README`.

Полноценный экран управления ставками сотрудников не реализовывался, так как это не указано в требованиях к интерфейсу.

### 3. Итоги по отфильтрованному списку на экране табеля

Фразу «итоги по отфильтрованному списку часы и стоимость» я интерпретирую как итоги по всем записям, которые подходят под текущие фильтры, а не только по записям текущей страницы.

### 4. Признак переработки

Переработка определяется по суммарному количеству часов сотрудника за календарный день. Если суммарно за день получилось больше 12 часов, день помечается как переработка.

Так как экран табеля отображает записи, а не сгруппированные дни, я возвращаю признак переработки для каждой записи, относящейся к такому дню. Если за один день у сотрудника несколько записей, все они могут быть отмечены как переработка.

12 часов ровно не считаются переработкой.

### 5. Процент освоения бюджета

Пороги «признак риска больше 80%» и «перерасход больше 100%» применяются к точному неокруглённому значению. В интерфейсе процент может отображаться округлённым до целого значения, как в примерах из задания 38%, 140%, 20%.

## Дополнительные допущения по модели данных и поведению

- Записи табеля не обязаны быть уникальными по паре сотрудник + проект + дата. Можно создать несколько записей за один день. Ограничение 24 часа проверяется суммарно по сотруднику за календарный день.
- История ставок должна быть непротиворечивой. Для одного сотрудника не должны создаваться две ставки с одной датой начала действия. Если такое редактирование где-то происходит, такие данные считаются конфликтом или ошибкой данных.
- Изменение ставки задним числом не запрещено закрытыми периодами, так как закрытый период блокирует только записи табеля, но не историю ставок.
- Проекты в рамках задания используются как справочные данные. Редактирование проектов, включая изменение дат начала и окончания, через интерфейс не реализовывалось.
- Отдельный административный экран закрытия и открытия месяца не является обязательным. Закрытие и открытие периода могут выполняться через соответствующие эндпоинты или скрипт. В интерфейсе важно показать понятную ошибку при попытке редактировать запись в закрытом периоде.
- Закрытый период блокирует создание, изменение и удаление записей табеля. Просмотр записей и построение отчётов остаются доступными.
- Запрос закрытия или открытия периода содержит год и месяц. Повторное закрытие или открытие периода считается идемпотентным и не является ошибкой.
- В ответах списка записей, кроме требуемых ФИО, шифра проекта, часов, ставки и стоимости, возвращаются поля, необходимые для интерфейса `id`, дата, комментарий и признак переработки.
- Пагинация возвращает не только массив элементов, но и служебную информацию для навигации общее количество записей, номер страницы и размер страницы.
- Для ошибок бизнес-правил используется ответ с кодом состояния 400 или 409 и телом вида `{ code ..., message ... }`, где код машиночитаемый, а сообщение на русском языке.
- Конкурентным считается только редактирование одной и той же записи табеля (TimeEntry). Для Update используется optimistic concurrency по паре Id + Version: версия возвращается при чтении и ожидается в запросе изменения, при несовпадении версии возвращается ошибка и изменение отклоняется. Операции Create и Delete не требуют передачи Version. При этом конкурентные Create и Update разных записей одного сотрудника за один день не получают строгой защиты дневного лимита: проверка выполняется последовательностью aggregate → check → write без транзакционной изоляции. Это осознанное ограничение тестового задания.
- Delete не проверяет дневную сумму часов и не ожидает Version. Закрытый период по-прежнему блокирует удаление.
- Агрегация часов за день выполняется по записям табеля. Строгая атомарность дневного лимита не гарантируется.
- В записи табеля хранятся поля `AppliedRate` (применённая ставка) и `Cost` (стоимость), оба типа `decimal` / MongoDB `Decimal128`. `Cost` вычисляется как `Hours × AppliedRate` с округлением до копеек. Списки и отчёты читают сохранённые значения, динамический пересчёт стоимости при чтении не выполняется.
- При изменении истории ставок служебный механизм пересчитывает `AppliedRate` и `Cost` во всех затронутых записях табеля. Повторный пересчёт идемпотентен. Существует риск частичного пересчёта при сбое, который устраняется безопасным повторным запуском.
- В документе сотрудника `Employee` хранится поле `RateRevision` — монотонный логический счётчик (целое число). Он увеличивается атомарно через `$inc` в той же операции обновления, которая изменяет `RateHistory`.
- В записи табеля `TimeEntry` хранится поле `RateRevision` — снимок ревизии расчёта, действовавшей на момент вычисления `AppliedRate` и `Cost`. Это позволяет определить, какие записи были пересчитаны по актуальной ревизии, а какие требуют обновления.
- Скрипт пересчёта получает новую ревизию как результат атомарной операции `$inc` на `Employee.RateRevision`. Эта ревизия передаётся в операцию обновления записей табеля.
- Пересчёт выполняется на стороне MongoDB через `UpdateMany` с aggregation update pipeline. Для каждого интервала `[from, nextRateFrom)` применяется новая ставка: `AppliedRate = rate`, `Cost = $round(Hours * rate, 2)`, `RateRevision = jobRevision`. Записи не загружаются в C#.
- При конкурирующих пересчётах обновление применяется только к записям, у которых `RateRevision < jobRevision`. Таким образом, более старый job не перезаписывает данные, уже обновленные более новой ревизией.
- Для миллионов записей диапазон дат разбивается на чанки (например, по месяцам или по сотрудникам). Каждый чанк обновляется отдельным `UpdateMany` без единой огромной транзакции. Повторный запуск безопасен, частичный прогресс допустим и устраняется при следующем запуске.
- В отчёте возвращаются оба признака риск и перерасход. В интерфейсе обязательна подсветка перерасхода. Отдельный бейдж риска не является обязательным и может не отображаться, если перерасход уже подсвечен.
- Бюджет проекта считается положительным. Если по каким-то данным бюджет равен нулю, процент освоения принимается равным 0, чтобы избежать деления на ноль.
- Все даты в системе считаются календарными датами без времени. Дата передаётся между клиентом и сервером в формате `yyyy-MM-dd`.
